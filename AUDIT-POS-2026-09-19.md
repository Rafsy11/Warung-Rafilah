# Audit Warung Rafilah POS — 19 September 2026

Basis: handover pengguna dan checkout commit `1be77f2`. Pemeriksaan kode, SQL, konfigurasi Docker, skrip Linux, serta lint dan TypeScript lokal. Tidak mengubah kode aplikasi atau data. Lingkungan audit Windows; tidak mengakses PC Linux Mint, domain produksi, database produksi, printer, atau akun pelanggan. Temuan kode bukan bukti bahwa kerugian atau penyalahgunaan sudah terjadi.

P1 = perlu diprioritaskan karena memengaruhi uang, keamanan, atau pemulihan data. P2 = penting untuk keandalan dan operasional. Skenario di bawah merupakan reproduksi yang disarankan di database uji, bukan transaksi yang sudah dijalankan.

Konfirmasi pengguna selama audit: folder ini sama dengan versi yang berjalan di Linux Mint; domain/tunnel Cloudflare masih aktif; saat ini hanya satu pengguna; backup berada di PC Linux Mint yang sama dan belum pernah diuji restore; belum ada kejadian transaksi ganda, stok/laba meleset, kehilangan data, atau gagal setelah mati listrik yang dilaporkan. Artinya backup terpisah dan pembuktian restore menjadi prioritas nyata. Risiko konkurensi berpeluang lebih kecil, tetapi tetap mungkin dari tab/request yang tumpang tindih. Tidak ada kesimpulan bahwa data produksi telah rusak.

## Temuan prioritas tinggi

### 1. P1 — Deployment mengganti PIN admin ke nilai tetap dalam repositori

Bukti: `deploy-update.sh:58–69`. Setiap skrip dijalankan, `core.users` untuk username admin diperbarui menggunakan PIN literal. Nilainya sengaja tidak disalin dalam laporan.

Dampak: PIN yang diganti pemilik dapat kembali ke nilai yang diketahui pembaca kode. Jika skrip digunakan pada produksi dan login dapat diakses pihak lain, ini menjadi risiko pengambilalihan akun.

Perbaikan: hapus reset PIN dari deployment biasa, rotasi PIN produksi melalui prosedur khusus, dan periksa akses repositori serta riwayatnya. Belum dikonfirmasi apakah skrip ini dipakai di Linux Mint.

### 2. P1 — Total pembayaran tidak dihitung ulang dari detail produk di server

Bukti: `app/app/api/sales/route.ts:113`, `:159–175`, `:259–268`. Header penjualan memakai `total_amount` dari request; detail penjualan memakai harga master/tier yang dihitung server. Tidak ada rekonsiliasi keduanya.

Skenario: keranjang memuat harga Rp10.000, kemudian harga master berubah menjadi Rp12.000 sebelum checkout. Header tetap Rp10.000, detail menjadi Rp12.000. Request yang sengaja dimodifikasi juga dapat membuat total lebih rendah.

Dampak: struk, omzet, laba, hutang, dan pembayaran dapat berbeda untuk transaksi yang sama. Perbaikan: hitung seluruh total di server sebelum membuat penjualan, lalu kirim snapshot final ke UI dan pencetakan.

### 3. P1 — Validasi hubungan nominal pembayaran belum lengkap

Bukti: `app/app/api/sales/route.ts:8–36`, `:141`, `:156–157`. Tidak ada aturan server bahwa uang tunai mencukupi, kembalian sesuai, DP bon tidak melebihi tagihan, dan tunai split tidak melebihi total. Item juga boleh tanpa product_id dan tanpa digital_details sehingga bisa tidak diproses dalam loop.

Skenario: bon Rp10.000 dengan DP Rp20.000 menghasilkan `debtAdded = -10000`, sehingga mengurangi hutang lama. Split tunai lebih besar dari total menghasilkan komponen QRIS negatif.

Perbaikan: validasi silang berdasarkan metode pembayaran dan jenis item; tambahkan constraint database yang relevan. Validasi UI saja tidak cukup.

### 4. P1 — Retry checkout dapat membuat transaksi ganda

Bukti: `app/app/api/sales/route.ts:111` membuat kode baru setiap request; `app/app/page.tsx:382–390` tidak mengirim identitas checkout yang stabil. Tidak ditemukan idempotency key pada jalur ini.

Skenario: COMMIT berhasil, respons terputus, kasir mencoba lagi. Transaksi kedua kembali memotong stok dan mencatat penjualan/bon.

Perbaikan: ID permintaan stabil yang disimpan dengan unique constraint dan respons transaksi lama ketika request diulang. Tombol disabled di browser tidak menyelesaikan respons yang hilang.

### 5. P1 — Pembatalan QRIS otomatis bisa memberi pesan sukses palsu

Bukti: `app/app/api/sales/cancel/route.ts:7` hanya mengizinkan owner; `app/components/pos/QrisPaymentModal.tsx:55–65` tidak memeriksa `res.ok` dan tetap memanggil onCancel setelah respons 403 atau kegagalan jaringan.

Dampak: untuk akun cashier, timer dapat mengaku transaksi dibatalkan padahal tetap pending dan stok sudah dipotong. Penutupan/refresh browser juga menghilangkan state pending pada `app/app/page.tsx:73`; timer bukan proses server yang bertahan setelah browser ditutup.

Perbaikan: selaraskan otorisasi pembatalan transaksi milik kasir, periksa hasil server, sediakan daftar pending yang dapat dipulihkan serta kedaluwarsa server yang aman terhadap pembayaran terlambat.

### 6. P1 — Penjualan pending/void tetap menimbulkan kewajiban konsinyasi

Bukti: `app/app/api/sales/route.ts:270–279` langsung membuat kewajiban unpaid, termasuk ketika QRIS pending. `app/app/api/sales/cancel/route.ts` mengembalikan stok dan mengubah sale menjadi voided tanpa membalik kewajiban itu. `app/app/api/consignment/ledger/route.ts` menjumlahkan/melunasi ledger tanpa memfilter status penjualan.

Dampak: barang titipan yang batal dibeli tetap dapat ditagihkan sebagai setoran. Perbaikan: posting kewajiban saat sale selesai, atau reversal atomik dan penyaringan status yang konsisten.

### 7. P1 — Pelunasan hutang lewat AI melewati buku hutang

Bukti: `app/app/api/ai/command/route.ts:143–150`. Jalur SETTLE_DEBT_EXEC hanya mengubah current_debt; tidak INSERT debt_ledger, tidak transaksi/row lock, dan tidak memastikan nominal positif. Bandingkan jalur normal `app/app/api/customers/[id]/pay-debt/route.ts`.

Dampak: saldo berkurang tetapi riwayat pembayaran dan perhitungan uang saat tutup shift tidak mengetahui pembayaran. Dua pelunasan bersamaan juga dapat memakai saldo awal yang sama.

Perbaikan: seluruh pelunasan UI dan AI menggunakan satu fungsi transaksi yang memvalidasi, mengunci pelanggan, menulis ledger, dan mengaitkan pembayaran ke shift/metode pembayaran.

### 8. P1 — Saldo float tidak aman untuk transaksi bersamaan

Bukti: `app/app/api/agent/float-balance/route.ts:35–51`, `app/app/api/agent/transactions/route.ts:94`, serta jalur sales/confirm/cancel mengunci baris ledger terakhir lalu INSERT baris baru. Tidak ditemukan lock saldo bersama yang stabil.

Skenario: A dan B membaca saldo awal yang sama; B menunggu lock baris lama, sementara A membuat baris baru. B dapat melanjutkan memakai saldo pada baris lama dan menulis saldo akhir yang tidak memasukkan mutasi A. Ledger kosong juga tidak menyediakan baris untuk dikunci.

Perbaikan: baris akun saldo tunggal yang dikunci setiap mutasi, atau advisory lock transaksi yang diterapkan pada SEMUA penulis float. Risiko ini dianalisis dari kode, belum direproduksi pada database uji. Semantik snapshot/row lock: [PostgreSQL 16](https://www.postgresql.org/docs/16/transaction-iso.html).

### 9. P1 — Migrasi startup tidak menjamin transaksi pada koneksi yang sama

Bukti: `app/lib/db.ts:65–77` menggunakan pool.query untuk BEGIN, SQL migrasi, pencatatan migrasi, dan COMMIT. Startup migrasi berjalan asinkron tanpa gerbang kesiapan request; kegagalan dicatat lalu proses berlanjut. Panduan [node-postgres](https://node-postgres.com/features/transactions) mewajibkan satu client untuk satu transaksi.

Tambahan konkret: `app/migrations/021_product_price_history.sql:54` mencatat filename sendiri, kemudian runner memasukkan filename yang sama tanpa ON CONFLICT. Berkas itu juga menjalankan BEGIN/COMMIT sendiri. Runner dapat melaporkan error setelah perubahan migrasi sudah terlanjur committed.

Perbaikan: runner khusus dengan satu client, satu pemilik transaksi dan pencatatan, lock migrasi, fail-fast, serta readiness yang menunggu migrasi selesai. Dockerfile tidak menyalin migrations secara eksplisit; keberadaan folder dalam image standalone perlu diverifikasi, bukan diasumsikan pasti hilang.

### 10. P1 — Backup dapat dianggap berhasil walaupun pg_dump gagal

Bukti: `scripts/backup-db.sh:10`, `:21–27`: set -e tanpa pipefail, pipeline pg_dump | gzip, langsung menyatakan sukses lalu menghapus backup lama.

Dampak: ketika docker exec/pg_dump gagal tetapi gzip sukses, file gzip tanpa dump yang berguna tetap dibuat dan rotasi tetap berjalan. Skrip juga memakai path tetap dan Docker context aktif; keberhasilan cron dengan context desktop-linux belum terbukti.

Perbaikan: pipefail, file sementara lalu rename setelah validasi, kegagalan menghentikan rotasi, context eksplisit, monitoring hasil, backup di media/perangkat terpisah, dan uji restore berkala. Pengguna mengonfirmasi backup berada pada PC yang sama dan belum pernah diuji restore: kerusakan/kehilangan PC atau disk dapat menghilangkan database beserta backupnya.

### 11. P1 — Laporan laba menyembunyikan rugi dan menghitung ulang kerugian lama memakai modal sekarang

Bukti: `app/app/api/reports/net-profit/route.ts:39` memaksa gross_margin minimal nol. Pada `:74–79`, kerugian barang rusak/kedaluwarsa memakai p.cost_price terkini.

Skenario: margin -Rp20.000 ditampilkan sebagai nol; mengubah modal produk kemudian mengubah kerugian laporan periode lama.

Tambahan bersyarat: biaya konsinyasi paid dikurangi lagi pada `:94–104`, sementara modal produk sudah masuk COGS. Jika cost_price barang titipan juga berisi bagian supplier, biaya dapat dihitung dua kali. Konvensi input modal barang titipan perlu ditanyakan.

Perbaikan: pertahankan margin negatif, snapshot modal pada mutasi kerugian, dan tetapkan perlakuan konsinyasi yang konsisten antara kewajiban, HPP, dan pembayaran. Label net profit saat ini juga belum mencakup biaya operasional seperti listrik/sewa yang tidak masuk rumus.

### 12. P1 — Kas tutup shift dapat memasukkan pelunasan milik kasir lain

Bukti: `app/app/api/cashier-sessions/close/route.ts:80–88` menjumlahkan seluruh debt_paid sejak opened_at, tanpa session_id, created_by, atau metode pembayaran.

Dampak: bila shift tumpang tindih, satu pelunasan dapat dihitung pada beberapa laci. Jalur pelunasan juga tidak menyimpan metode pembayaran, sehingga semua dianggap tunai.

Perbaikan: hubungkan setiap penerimaan kas ke shift/laci dan metode pembayaran. Ada risiko tambahan checkout bersamaan dengan penutupan: checkout membaca shift tanpa lock bersama, dan konfirmasi QRIS tidak memeriksa shift sudah ditutup. Nilai closing bisa menjadi kedaluwarsa.

## Temuan lanjutan

### 13. P2 — Tag sumber perubahan harga tidak berada dalam transaksi UPDATE

Bukti: `app/app/api/ai/command/route.ts:660–661` dan reaktivasi `app/app/api/products/route.ts:91`. set_config(..., true) bersifat lokal terhadap transaksi tetapi dipanggil dalam statement terpisah tanpa BEGIN yang meliputi UPDATE. Reaktivasi juga menggunakan pool.query.

Dampak: label ai_command/reactivation tidak terjamin terbaca oleh trigger. Trigger hanya memakai COALESCE tanpa normalisasi string kosong; perilaku saat setting direset dan CHECK source perlu diuji di PostgreSQL 16. Perbaikan: satu client dan transaksi, setting sebelum UPDATE, serta fallback source tervalidasi. Klaim handover tentang tagging menyeluruh belum terbukti.

### 14. P2 — Stok dapat berubah tanpa jejak mutasi yang lengkap

Bukti: `app/app/api/sales/route.ts:335` memotong stok tanpa INSERT movement sale; pembatalan mengembalikan stok tanpa movement void_return. Tidak ditemukan trigger stok pada SQL yang diperiksa. `app/app/api/products/[id]/route.ts` membolehkan patch stock_qty langsung tanpa ledger dan hanya memvalidasi nama field, bukan nilai.

Dampak: riwayat mutasi tidak dapat menjadi rekonsiliasi penuh stok. Harga/stok negatif juga tidak ditolak oleh validasi numerik endpoint tersebut dan tidak memiliki CHECK yang relevan di schema dasar.

Perbaikan: semua perubahan stok melalui fungsi terpusat yang mencatat delta, alasan, aktor dan referensi; validasi nilai di API dan database.

### 15. P2 — Penguncian stok pada konversi dan AI tidak mencakup seluruh operasi

Bukti: auto-convert `app/app/api/sales/route.ts:289–311` membaca stok kemasan sumber tanpa row lock, lalu mengurangi tanpa syarat stok mencukupi. Dua produk tujuan yang memakai sumber sama bisa berlomba. Jalur AI `app/app/api/ai/command/route.ts:156` menjalankan FOR UPDATE sebelum BEGIN pada baris 168 sehingga lock tidak melindungi pemeriksaan sampai UPDATE.

Perbaikan: lock semua produk yang terlibat dalam transaksi yang sama, urutan lock konsisten, dan update bersyarat untuk menjaga stok nonnegatif.

### 16. P2 — Struk bon menghilangkan DP yang sudah dibayar

Bukti: `app/app/page.tsx:431` memaksa payment_received menjadi nol untuk DEBT. Printer sebenarnya sudah mendukung DP pada `app/app/api/print/route.ts`.

Skenario: belanja Rp100.000, DP Rp30.000. Hutang database Rp70.000, tetapi struk mencetak sisa bon Rp100.000. Perbaikan: cetak snapshot server termasuk DP dan sisa bon; jangan bangun bukti transaksi dari state keranjang saja. Struk terakhir juga hanya tersimpan di ref browser sehingga hilang setelah reload.

### 17. P2 — Pembatasan login berbeda dari klaim handover

Bukti: `app/app/api/auth/login/route.ts:63` memakai key username+IP, bukan username lintas IP. Jadi batas lima percobaan bukan batas per akun global. `app/lib/audit-logger.ts` mempercayai header IP; tingkat spoofability bergantung proxy aktual.

`app/lib/rate-limiter.ts:86` hanya menghapus entry dengan attempts.length === 0, tetapi cleanup tidak membuang timestamp kedaluwarsa. Key unik yang tidak digunakan lagi tetap tersimpan. Ini risiko pertumbuhan memori pada proses dengan heap 180 MB.

Perbaikan: batas akun dan IP terpisah, trust proxy jelas, serta pembersihan timestamp/key kedaluwarsa. Belum dilakukan simulasi serangan pada domain produksi.

### 18. P2 — Logout dan penonaktifan pengguna tidak mencabut token yang sudah diterbitkan

Bukti: `app/app/api/auth/login/route.ts` menerbitkan JWT berlaku 24 jam; `app/middleware.ts` hanya memverifikasi tanda tangan/kedaluwarsa; logout hanya menghapus cookie browser.

Dampak: salinan token yang sudah diperoleh tetap berlaku sampai kedaluwarsa, termasuk setelah akun dinonaktifkan atau role diubah di database. Perbaikan: versi sesi/revocation atau sesi server dengan pengecekan pengguna aktif. Ini tidak berarti token sudah bocor.

### 19. P2 — Private key TLS dilacak Git

Bukti: `git ls-files ssl` mengembalikan ssl/key.pem dan ssl/cert.pem. Isi key tidak dicetak dalam laporan.

Dampak tergantung pemakaian dan akses repositori: jika key ini digunakan di Linux, orang yang memperoleh repositori juga memperoleh private key itu. Perbaikan: keluarkan secret dari tracking, buat key per instalasi, dan rotasi key yang digunakan. Belum dipastikan apakah sertifikat ini aktif atau sekadar artefak development.

### 20. P2 — Healthcheck belum menguji kemampuan POS bertransaksi

Bukti: `app/app/api/health/route.ts` hanya mengembalikan ok dan uptime proses. `gui/start-pos-gui.sh` memeriksa container berjalan dan curl tanpa pemeriksaan HTTP gagal, lalu dapat menyatakan POS started.

Dampak: database atau migrasi bermasalah tetapi launcher/health masih terlihat sehat. Perbaikan: pisahkan liveness dan readiness, cek DB/schema, timeout yang jelas, dan tampilkan kegagalan kesiapan. Self-healing container bukan pengganti backup atau uji pemulihan mati listrik.

### 21. P2 — Mode offline dan QR di layar perlu diperjelas

`app/public/sw.js` melewati semua request API; halaman transaksi tetap bergantung backend. Ini cocok untuk internet putus selama server lokal berjalan, tetapi bukan transaksi yang tetap berjalan saat backend lokal mati. Keranjang/pending checkout berada dalam state browser, belum ada jurnal pemulihan checkout.

`app/components/pos/QrisPaymentModal.tsx` menggambar pola SVG dekoratif, bukan payload QRIS, dengan aria-label seolah kode QRIS. Teks bawah memang meminta pelanggan memakai QR statis fisik. Perbaikan UX: tampilkan QR merchant asli atau hapus gambar dekoratif yang membingungkan. Konfirmasi pembayaran saat ini manual dan webhook QRIS dinonaktifkan; apakah itu sesuai kebutuhan perlu dikonfirmasi.

### 22. P2 — Gerbang kualitas dan pengujian belum memberi jaminan regresi

Hasil aktual pada lingkungan audit:

- `npm.cmd run lint -- --quiet`: gagal, 78 error. Termasuk any, aturan hooks, dan impor require. Angka ini bukan 78 bug runtime.
- `node node_modules/typescript/bin/tsc --noEmit --incremental false`: gagal, html5-qrcode tidak ditemukan dan dua parameter implisit any di CameraScannerModal.tsx. Dependency tercantum di package.json, sehingga instalasi node_modules lokal mungkin belum sinkron; belum dapat disimpulkan build Linux gagal.
- Tidak ditemukan berkas pengujian aplikasi dalam pencarian nama test/spec dan tidak ada script test di package.json.
- Build produksi, uji integrasi DB, restore, printer, aksesibilitas visual, dan uji mati listrik belum dilakukan.

Perbaikan: mulai dari pengujian invariant total, retry checkout, bon, QRIS batal, konsinyasi, mutasi bersamaan, dan restore. Lint/typecheck yang bersih menjadi gerbang sebelum deployment.

2. Apakah domain aktif dilindungi Cloudflare Access, dan apakah repo publik atau privat?
3. Apakah satu pengguna tersebut memakai akun owner dan lebih dari satu tab/perangkat bersamaan?
4. Jadwal, Docker context, dan skrip backup yang benar-benar dijalankan? Lokasi satu PC dan belum pernah restore sudah dikonfirmasi.
5. Fitur yang aktif digunakan: AI mutasi, bon/DP, konsinyasi, konversi stok, agen, dan QRIS? Modal barang titipan diisi bagaimana?
6. Spesifikasi PC, UPS, ruang disk, cara startup, serta kejadian nyata kehilangan transaksi/stok atau gagal setelah mati listrik?

## Urutan tindak lanjut

Amankan kredensial deployment dan verifikasi backup dapat direstore. Berikutnya satukan perhitungan server dan idempotency checkout, perbaiki QRIS/konsinyasi serta buku hutang AI. Setelah itu selesaikan locking saldo/stok/shift, migrasi yang deterministik, dan koreksi laporan. Lakukan pada database uji sebelum penerapan Linux Mint.

Hal positif yang terlihat di kode: query utama memakai parameter SQL; middleware menghapus header identitas dari client; checkout utama memakai client transaction; harga modal penjualan disnapshot; stok item utama menggunakan update bersyarat; beberapa layanan Docker dibatasi loopback. Perlindungan ini berguna, tetapi tidak meniadakan temuan di atas.

Hasil verifikasi lokal:

- PostgreSQL **16.15** sementara: **13 tes lulus**, tidak ada kegagalan/skip. Mencakup permintaan bersamaan, replay checkout, saldo, shift, bon, pembatalan konsinyasi, sesi, validasi modal/stok, laporan kerugian, dan rollback migrasi gagal.
- Migrasi dari skema sebelum 022, dijalankan ulang: seluruh nilai kolom lama pada **22 tabel operasional** tetap sama, diperiksa dengan jumlah baris dan hash isi.
- `pg_dump -Fc` dan `pg_restore --exit-on-error` nyata berhasil pada data uji; pemeriksaan salinan setelah restore juga berhasil.
- Backup gagal ketika dump gagal; backup sukses menghasilkan salinan eksternal identik dalam pengujian script.
- Build Next.js produksi dan pemeriksaan TypeScript berhasil. Lint tidak memiliki error; masih terdapat warning nonfatal (impor/variabel tidak dipakai dan dependency hooks), bukan klaim lint tanpa warning.
- Sintaks seluruh shell script yang diubah serta `git diff --check` diperiksa.

Batas: Docker daemon lokal tidak tersedia, sehingga image/container Linux dan keseluruhan deployment belum dijalankan di sini. Pemeriksaan browser terbatas berhasil setelah server uji dimulai ulang: login, daftar produk, keranjang desktop, checkout QRIS, recovery transaksi setelah reload, dan modal pada viewport 390×844. Ini belum merupakan pengujian menyeluruh seluruh layar. Printer, laci, Cloudflare Access, jadwal backup eksternal, restore data produksi, dan mati listrik perlu diverifikasi pada PC kasir. Tidak ada data historis yang direkonstruksi dengan tebakan dan tidak ada database produksi yang disentuh. Langkah penerapan dan penanganan kegagalan terdapat di [UPGRADE-SAFE.md](UPGRADE-SAFE.md).
